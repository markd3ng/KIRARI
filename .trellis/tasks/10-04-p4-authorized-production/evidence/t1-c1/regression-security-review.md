## Confirmed issues and fixes

- **npm executable shadowing (fixed).** Before hardening, both the installer and audit collector invoked `npm` through inherited `PATH`. I reproduced a PATH-shadow using a temporary fake executable; the collector accepted its synthetic zero-count output and reported the command as executed. The current [`npm-runtime.mjs`](/Users/ian/.codex/worktrees/p4-t1-c1/KIRARI/scripts/p4-production/npm-runtime.mjs) runs `process.execPath` with the adjacent npm CLI script and measures its SHA-256. The current Production workflow also invokes later JavaScript by the absolute Node 22.12.0 setup-node path. I ran `p4-tooling-gate.test.mjs` under that exact runtime: 5/5 pass, including an actual fake-`npm` PATH attempt that does not execute the fake.
- **Workflow shell startup injection (fixed).** The root/P3 install steps run before the credential-bearing step, and a prior lifecycle can write shell environment files. A `BASH_ENV` payload runs before a noninteractive `bash --noprofile --norc -e -o pipefail` script. The latest Production workflow explicitly sets `BASH_ENV` and `ENV` to `/dev/null`, and clears `NODE_OPTIONS`, `NODE_PATH`, `LD_PRELOAD`, and `LD_LIBRARY_PATH` on every `run:` step, including the token-bearing step. The workflow regression demonstrates an inherited loader runs without the override and does not run with the operation-step overrides. I ran `p4-production-workflow.test.mjs` under Node 22.12.0: 9/9 pass. GitHub documents that `GITHUB_ENV` is applied to later steps and specifically blocks setting `NODE_OPTIONS`; this review therefore treats `BASH_ENV` as the concrete shell vector and does not claim that `NODE_OPTIONS` can be set through that file. [GitHub workflow commands](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands)
- **Audit result/count inconsistency (fixed).** A synthetic npm v2 report with a qualifying vulnerability and exit code 0 initially passed. The evaluator now checks complete report schema/counts against the plain and JSON command exits and fails inconsistent evidence. The negative regression is in [`p4-production-tooling-acceptance.test.mjs`](/Users/ian/.codex/worktrees/p4-t1-c1/KIRARI/scripts/tests/p4-production-tooling-acceptance.test.mjs). Raw audit status and P4 acceptance remain separate; the commands are unconditional, and advisory suppression is not introduced.
- **Owner decision mutation/revocation (fixed).** The readback requires an exact JSON decision from `markd3ng` on the expected issue, author association `OWNER`, an exact manifest digest, finite UTC expiry, and an unedited comment. It scans the full bounded comment history; later Owner statements invalidate the prior decision, and incomplete/unreadable scans fail closed. The evaluator requires a recent clear revocation readback and a separate concrete approval. The production job now has only the additional `issues: read` permission needed for this API read; all unspecified `GITHUB_TOKEN` permissions are none when explicit permissions are present. [GitHub workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
- **Advisory review substitution/omission (fixed in evaluator).** The review matrix binds every npm audit package/advisory/inherited reference to package, directness, path, effects, range, fix data, and source `via` record; exact row counts, unique record IDs, analysis, and unknown-path disclosure are required. Missing, substituted, duplicate, or stub rows fail closed.
- **Pre-credential source binding (closed in current manifest).** The current T1 manifest binds 20 material inputs, including both workflows, root pnpm manifest/lock/workspace, P3 browser manifests, npm runtime/install/gate/evaluator, Owner and C1 gate/contract, deployment/runtime code, and T1 package manifest/lock. I recomputed all 20 SHA-256 values against the current worktree; they match the manifest. This closes the earlier omission of root/P3 install graphs.
- **C1 self-asserted static readback (fixed fail-closed).** The static C1 file is only an incomplete template. `evaluateCurrentCredential` obtains observations only from an authenticated reader callback; the current operational gate supplies none, so it cannot claim current principal, plan, roles, access groups, grants, PAT scope, or expiry. The exact-project validator rejects Owner/Member/Admin elevation, direct or group-derived Project Admin, extra extended grants, incomplete evidence, unknown scope, missing expiry, stale/different readback, and token-like values. Endpoint granularity remains `UNKNOWN`, and undocumented role-scope semantics remain explicitly an inference.
