## Existing implementation, reuse, and risks

- `workers/kirari-edge/src/index.ts:43` implements flag-gated prefixes `/api/github`, `/avatar`, `/api/bangumi`, `/images/bangumi`; its master/feature flags default off (`:83`, profile `:1073–1105`). It is a stateless Worker, not the proposed capability core. `wrangler.jsonc:1` has no KV/cache bindings. Live Worker deployment, effective flags, token existence/scope, origins and production routing remain **UNKNOWN**.
- **Confirmed local URL-construction defect:** `index.ts:150` passes arbitrary stripped suffix to `new URL(pathname, origin)`. `/api/github//example.invalid/path` resolves to `https://example.invalid/path`; reproduced with the identical WHATWG URL expression on Node 22, without network. `:50–54` attaches the GitHub token before fetch (`:171`). If that route and a token are enabled, a caller can direct a credential-bearing initial request off the approved host. No live exploit or live credential check performed. Replacement must reject before fetch and test duplicate slashes/encoded separators/authority changes; this defect should also be triaged as a standalone narrowly scoped Worker fix if Gateway work is deferred.
- Worker forwards arbitrary suffix/query (`:150–152`), uses wildcard CORS (`:25`), has no explicit response-byte bound, fetch timeout, health route, cache backend, or status-sensitive error caching. It overwrites upstream cache headers even for errors (`:177–185`). Existing tests assert prefix stripping/header handling and defaults, not capability confinement (`workers/kirari-edge/test/index.test.ts:118,136,161`).
- Existing **Vercel GitHub template is useful prior art**, not missing functionality: `apps/site/adapters/github-card/vercel/route.ts.template:7` models four named route kinds; `:24` read-only methods; `:34` eight-second timeout; `:111` avatar size bound; `:120` fixed upstream construction; `:142` REST-only token; `:166` rate-limit headers; `:189` per-kind success/404/no-store policy; `:199` versioned keys; `:210` explicit allowed-origin headers. It still buffers entire responses (`:159`), lacks exhaustive query/ref bounds, and couples `process.env`, routing, cache headers and semantics in one template. Its `X-Cache: VERCEL-CDN` is a label, not observed cache-hit evidence.
- Existing Cloudflare template (`apps/site/adapters/github-card/cloudflare/route.ts.template:18`) rewrites `/ghc` to Worker `/api/github` and delegates via Service Binding; it inherits that Worker's broad semantics. `apps/site/scripts/materialize-ghc-adapter.mjs:11` generates either platform template behind explicit opt-in and removes generated routes. Keep that generation ownership; do not hand-edit emitted `functions/` or `api/` files.

## Minimal #102 proposal for a separately authorized task

1. Freeze only the five caller-backed operations above under `/_kirari/edge/*`; write a small operation table/parser, not a general proxy/router framework. Each route accepts GET/HEAD, deliberate OPTIONS handling, fixed upstream construction, named parameters and exhaustive query allowlists. Repository accepts no query; contents permits `ref`; latestCommit permits bounded `path`/`sha` with fixed `per_page=1`; avatar permits bounded `size`; collections starts with caller-required `limit=24` (additional pagination only after a caller exists). Pin numeric name/ref/path/body/time bounds in the reviewed contract and fixtures before implementation.
2. Core owns validation, canonical request/cache key, approved upstream URL/header selection, bounded fetch/response, normalized errors, rate-limit visibility and health response. Use Web `Request`/`Response`/`fetch`; inject approved fetch/token/cache capabilities. No `process.env`, Cloudflare types, Vercel packages, storage bindings or provider route packaging in core. Never forward a browser credential; never attach a GitHub REST token to avatars/Bangumi; constrain redirects as well as the initial host.
3. Keep adapter responsibilities to handler translation, route packaging, environment-scoped binding acquisition, cache backend and lifecycle hooks actually supported by that runtime. Define `EdgeCache` and `PersistentCache` capabilities with availability, TTL, version/invalidation, consistency and failure/downgrade behavior; `CACHE_NONE` is the honest default until backend behavior is verified. Do not equate stale HTTP directives with implemented stale fallback or persistence.
4. Integrated same-origin routing is default. Standalone mode requires an explicit allowed-origin set and separate health/cache lifecycle; no wildcard CORS. New Site selection should be platform-neutral `enabled`/`base`/feature flags. Existing provider-specific `githubCard.adapter` fields are migration input, not the target cross-platform config contract. Decide temporary `/ghc` compatibility explicitly and avoid assuming the Worker `/api/github` is equivalent.
5. First tests: invalid method/path/query/encoding and host-escape rejection before fetch; token sent only to approved REST; input/time/body caps; success/short-404/error policies; no-secret errors/logs; cache capability downgrade; enabled/disabled routing and standalone CORS. Then adapt the existing four GitHub operations, add only userCollections, and package runtimes in separate #110–112 tasks.

| Historical/current behavior | Migration classification |
|---|---|
| Four GitHub operations; read-only handling; validation; rate-limit visibility; health; kind TTL and short-404/no-store rules | **KEEP** the contract; Vercel template supplies several concrete implementations, health needs a clear response contract. |
| Secrets, cache backends, version/invalidation, stale fallback, handler lifecycle and packaging | **ADAPT** behind runtime boundary; stale fallback/persistent cache are requirements, not established current Worker behavior. |
| Broad suffix/query forwarding; authority-changing URLs; current `/ghc` target namespace | **REPLACE** with named operations and fixed upstreams; `/ghc` only deliberate temporary compatibility. |
| Scheduled prewarm; wildcard CORS; equivalence claims for cache platforms; unconsumed proxy operations | **DROP** from MVP. No current scheduled handler was found; this also addresses the historical #102 migration requirement. |
