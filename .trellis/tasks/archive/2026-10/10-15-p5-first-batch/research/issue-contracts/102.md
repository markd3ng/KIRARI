# #102 [RM-08] Establish the KIRARI Edge Gateway capability core and migrate GHCardCache contracts

## Architecture clarification — 2026-10-15

KIRARI uses the hosting provider's native deployment mechanism. GitHub Actions validates source and produces optional portable artifacts, but does not duplicate the provider's native release controller.

Optional Gateway capability development depends only on completed #95–97 Core/Site configuration contracts; it does not replace Site hosting or inherit P4 admission. #110–112 inherit capability/security/cache requirements only.

GOAL
Establish the portable KIRARI Edge Gateway capability core and migrate the reusable KIRARI-GHCard-Cache contracts without turning the Worker into a general-purpose reverse proxy.

SCOPE
- Inventory current Site callers and distinguish active requirements from merely implemented, disabled proxy routes. Current active GitHub card operations are repository metadata, contents, latest commit by path, and avatar fallback. The Bangumi page currently calls user collections directly and consumes nested subject/image data; a separate `bangumi.subject`, `bangumi.image`, `avatar.resolve`, or Cravatar operation is only a candidate until a caller or owner decision confirms it.
- Define named capabilities and explicit route/method/path/query/upstream allowlists under the proposed `/_kirari/edge/*` namespace. Reject arbitrary target URLs and arbitrary path suffix forwarding. Example operations: `github.repository`, `github.contents`, `github.latestCommit`, `github.avatar`, and `bangumi.userCollections`; only add candidate operations with demonstrated need.
- Specify strict input/response bounds, read-only methods, token boundaries, rate-limit visibility, health behavior, and cache/error policy. GitHub credentials may be used only on approved upstream REST calls and must not appear in client responses or logs.
- Define a platform-neutral core over Web `Request`, `Response`, and `fetch`, with runtime route, secret binding, cache backend, and packaging kept in platform adapters.
- Define `EdgeCache` and `PersistentCache` capability contracts with `CACHE_NONE`, `CACHE_EDGE`, and `CACHE_PERSISTENT` levels. Preserve platform-specific scope, consistency, invalidation, TTL, and downgrade behavior; do not assert equivalent semantics.
- Record two modes: integrated same-origin `/_kirari/edge/*` as the default; standalone `edge.example.com` with explicit allowed origins, independent lifecycle, health, and cache policy.
- Keep Site configuration platform-neutral: it may select `enabled`, a same-origin `base`, and feature flags, but never Cloudflare/Vercel/EdgeOne behavior.
- Include a GHCardCache migration matrix (`KEEP`, `ADAPT`, `REPLACE`, `DROP`) and make `/ghc/*` compatibility a deliberate temporary choice, not a permanent promise.

OUT_OF_SCOPE
- General-purpose reverse proxy behavior such as user-controlled upstream URLs or arbitrary forwarded paths.
- Cloudflare, Vercel, or EdgeOne runtime implementation; those are separately scoped by #110–#112.
- External Site export/Preview validation (#98), native Site hosting (#99), or any production Gateway deployment.
- Starting Gateway implementation as part of this Roadmap correction.

ACCEPTANCE_CRITERIA
- A source-backed caller/capability map distinguishes active GitHub card calls, the active Bangumi user-collections call, disabled/unreferenced proxy routes, and proposed operations.
- Every accepted route has an explicit method, path parameters, query allowlist, fixed upstream, token rule, input/output bounds, and failure/cache rule; invalid routes are rejected before upstream fetch.
- The portable core has no platform runtime/cache/secret imports; adapter contracts cover handler, routing, bindings, and packaging.
- Cache levels and per-platform differences are documented, including honest `CACHE_NONE` downgrade where a capability is unavailable or unverified.
- Integrated and standalone modes, CORS/origin handling, and platform-neutral Site config are specified.
- The historical migration matrix preserves safe useful behavior, replaces suffix forwarding, and drops scheduled prewarm and wildcard-CORS assumptions.
- Live Worker deployment, token scope, and production settings remain explicitly UNKNOWN until inspected.

DEPENDENCIES
P1 Issue #95 and the P2 Site input/config contract (#96 and #97). P5 work does not block P1 remote delivery. #110–#112 depend on this core contract. #98 owns Site artifact packaging/staging; it does not own Gateway runtime behavior.

DELIVERY_EVIDENCE
Caller map; capability and route contract; `KEEP`/`ADAPT`/`REPLACE`/`DROP` matrix; portable core/adapter boundary; cache semantics matrix; integrated/standalone and Site config contract; focused allowlist/token/cache tests; explicit UNKNOWN records for uninspected live settings.

HISTORICAL_IMPLEMENTATION

Adapt cache and secrets behind platform adapters. Replace `/ghc` as the target namespace and suffix forwarding. Drop scheduled prewarm and wildcard CORS assumptions.

Keep cache/token capabilities disabled or use CACHE_NONE until verified; do not substitute older classic EdgeOne Functions docs for Makers. https://pages.edgeone.ai/document/edge-functions ; https://pages.edgeone.ai/document/kv-storage ; https://pages.edgeone.ai/document/environment-variable ; https://pages.edgeone.ai/document/build-guide
