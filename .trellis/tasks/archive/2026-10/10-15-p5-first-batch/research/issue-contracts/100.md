# #100 [RM-06] Notify indexing only after verified native Production deployment

## Architecture clarification — 2026-10-15

KIRARI uses the hosting provider's native deployment mechanism. GitHub Actions validates source and produces optional portable artifacts, but does not duplicate the provider's native release controller.

Select a supported Vercel deployment webhook or Git-integrated deployment status only after validating its actual event/authenticity contract. Before indexing, verify exact project/team, Production environment, commit, deployment READY/success and canonical domain: Team team_NsBZHGUVnyygP7veiROKLuUx; project prj_QNMVdxTkPOad4ynN4fwFCYEST8Jk / kirari-main; repository markd3ng/KIRARI; Production branch main; canonical kirari-main.vercel.app. kirari-test is not Production. Generic main CI/local build/Preview/old artifact approval is insufficient. Reject wrong-project/environment/commit/domain, failed/incomplete, stale/replayed and unauthenticated signals. Indexing is opt-in, disabled by default, bounded and idempotent; Google eligible-content limits remain. This correction updates the contract, not the feature implementation.

Supported-signal research: [Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github#repository-dispatch-events) documents `repository_dispatch` type `vercel.deployment.success` and recommends migration from `deployment_status`. Evaluate that native integration first. A [signed Vercel webhook](https://vercel.com/docs/webhooks/webhooks-api) is another option; `deployment.succeeded` depends on registered checks. Neither event name alone proves Production identity or canonical serving. Transport selection, sender verification, authoritative metadata readback and replay tests belong to this issue; no new webhook, credential or workflow is provisioned by the architecture correction.

GOAL
Prevent official builds from notifying indexing services for content that has not successfully reached a verified native Production deployment.

SCOPE
Move IndexNow and any retained Google Indexing API submission out of postbuild into an opt-in post-deployment action; keep disabled by default; enforce the Google API eligible-content boundary; make failures bounded and observable without turning build success into an indexing claim.

OUT_OF_SCOPE
No notifications from local, test, external-Site CI, preview, or staging builds; no generic submission of ordinary BlogPosting URLs to an ineligible Google API; no provider enablement without owner approval.

ACCEPTANCE_CRITERIA
- Build and preview workflows make zero indexing requests regardless of submission flags.
- Notifications run only after verified successful native Production deployment and explicit provider opt-in.
- Google API requests are restricted to eligible approved content or remain disabled.
- Per-provider outcomes and bounded failures are recorded; retries cannot duplicate unboundedly.

DEPENDENCIES
RM-05; owner decides whether to retain IndexNow and whether any eligible Google Indexing API content exists.

DELIVERY_EVIDENCE
Network-captured build/preview zero-request checks, authorized post-deploy run record, provider outcome log and eligibility decision.
