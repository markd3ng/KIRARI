# F3 / F7 Dependency Security Review

Reviewed 2026-09-29 against the current lockfile and checked-in implementation. No dependency files were changed.

## F3 — Astro / AVIF

- **Installed:** `astro@6.4.8`. `pnpm why` resolves Astro's Sharp peer to `sharp@0.34.5`; KIRARI also directly installs `sharp@0.35.1`. Their platform binary packages resolve to `@img/sharp-libvips@1.2.4` / libheif `1.20.2` and `@img/sharp-libvips@1.3.0` / libheif `1.23.0`, respectively (`versions.json` in the installed packages). These are the actual decoder versions, not inferred from the top-level Sharp semver.
- **Advisories:** Astro GHSA-26w7-cxv4-gfx2 is Critical and affects Astro `<7.2.8`; fixed in `7.2.8`, whose advisory requires Sharp `0.35.4`. pnpm audit also reports Astro GHSA-376h-93r7-7g6f, GHSA-4g3v-8h47-v7g6, GHSA-f48w-9m4c-m7f5, and GHSA-7pw4-f3q4-r2p2 on `6.4.8`. Sharp GHSA-f88m-g3jw-g9cj affects `<0.35.0`; Sharp GHSA-rgj7-g3m4-5g8c affects `<0.35.4` because of libheif GHSA-g89c-p67h-r497 and GHSA-2jg2-4ch7-h545. The installed libheif `1.20.2` and `1.23.0` are also in ranges for later upstream issues, including GHSA-24wx-9w62-c96w and GHSA-x8r2-mggj-j6wr (fixed `1.23.3`), GHSA-xrp2-63fq-jm8q and GHSA-vg7w-rp49-4fc2 (fixed `1.23.4`), and GHSA-v8qw-hwjv-44hw (fixed `1.23.5`); `1.20.2` additionally falls within GHSA-4h82-g446-83fm (fixed `1.23.3`). Sources: [Astro RCE advisory](https://github.com/withastro/astro/security/advisories/GHSA-26w7-cxv4-gfx2), [Sharp audit/advisories](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c), [Sharp older libvips advisory](https://github.com/advisories/GHSA-f88m-g3jw-g9cj), [libheif RCE advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-2jg2-4ch7-h545), [libheif decompression advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-24wx-9w62-c96w), [libheif mixed-interleave advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-x8r2-mggj-j6wr), [libheif reference recursion advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-xrp2-63fq-jm8q), [libheif item-limit advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-vg7w-rp49-4fc2), [libheif AV1 allocation advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-v8qw-hwjv-44hw), [libheif sequence OOB advisory](https://github.com/strukturag/libheif/security/advisories/GHSA-4h82-g446-83fm).
- **Reachable path:** `astro.config.mjs` has no custom image service. `src/components/misc/ImageWrapper.astro` feeds local assets to Astro's `Image` component, and post cover metadata reaches that component through the post pages and `PostCard`. `profile-manifest.mjs` copies `content/posts/` and `assets/images/` as ordinary files without an image extension allowlist; post `image` is a string, and an external Site can supply an AVIF cover. Existing checked-in covers are JPEG; no current AVIF fixture was found. Therefore the decoder path is **CONDITIONAL** on an untrusted AVIF reaching a build, not a confirmed production exploit. The repository's documented model currently treats external Site input as trusted; build execution has no OS sandbox.
- **Compatibility / separate PR:** The fixed Astro version crosses from Astro 6 to 7. Astro's official v7 guide documents a Vite 8 change and Rust compiler becoming the default, with stricter markup behavior and likely integration/plugin compatibility work. Sharp `0.35.5` was released 2026-09-27 and `sharp-libvips@1.3.4` packages libheif `1.23.5`; this meets Astro's Sharp `0.35.4` minimum and includes the cited libheif fixes through `1.23.5`. The separate PR should use Astro `>=7.2.8`, Sharp `>=0.35.5`, and verify the actual platform libheif binary remains at a currently patched release; run profile check, site tests, type/Astro checks, default/external builds on Linux and macOS, plus a fresh advisory audit. Do not perform this upgrade in PR-1 remediation. Sources: [Astro v7 migration guide](https://docs.astro.build/en/guides/upgrade-to/v7/), [sharp-libvips v1.3.4 dependency versions](https://raw.githubusercontent.com/lovell/sharp-libvips/v1.3.4/versions.properties), [Sharp v0.35.5 release](https://github.com/lovell/sharp/releases/tag/v0.35.5).
- **Status:** `CONDITIONAL`; vulnerable versions and a reachable AVIF processing path are confirmed, while attacker control of the source image is not part of the intended trusted-input model. Treat as an unresolved security release gate until a separate compatibility-reviewed upgrade or a verified AVIF processing restriction is in place.

## F7 — tar

- **Installed:** `tar@7.5.16`, pinned by the root `pnpm.overrides.tar` and `pnpm-lock.yaml`.
- **Dependency chain:** `astro-icon@1.1.5 -> @iconify/tools@4.2.0 -> tar@7.5.16` (verified with `pnpm --filter @kirari/site why tar`).
- **Applicable advisories:** Installed `7.5.16` is affected by GHSA-gvwx-54wh-qm9j (fixed `7.5.17`, PAX NUL path crash), GHSA-w8wr-v893-vjvp (fixed `7.5.18`, PAX numeric path crash), GHSA-8x88-c5mf-7j5w (fixed `7.5.18`, negative-entry-size infinite loop), GHSA-23hp-3jrh-7fpw / CVE-2026-59873 (Critical, fixed `7.5.19`, decompression/parse resource exhaustion), and GHSA-r292-9mhp-454m / CVE-2026-73566 (High, affected through `7.5.20`, fixed `7.5.21`, recursive stack exhaustion when member filtering is used). The minimum candidate that clears all five pnpm-audit advisories is therefore `tar >=7.5.21` within the existing 7.x major line. Sources: [NUL-path advisory](https://github.com/advisories/GHSA-gvwx-54wh-qm9j), [PAX-path advisory](https://github.com/advisories/GHSA-w8wr-v893-vjvp), [negative-size advisory](https://github.com/advisories/GHSA-8x88-c5mf-7j5w), [Critical resource-exhaustion advisory](https://github.com/advisories/GHSA-23hp-3jrh-7fpw), [recursive stack-exhaustion advisory](https://github.com/advisories/GHSA-r292-9mhp-454m).
- **Reachability:** `@iconify/tools` exposes `downloadNPMPackage`; its `untar()` helper calls `tar.x()`. Current KIRARI code only configures local `@iconify-json/*` collections, and `astro-icon`'s local loader uses `importDirectory`/SVG processing. No current app caller invokes the NPM icon download/extraction API. Thus the vulnerable extraction sink is present in a build-time dependency but **NOT_REACHABLE** through the checked-in default build path. It becomes **CONDITIONAL** if tooling invokes that download API on untrusted archive content. This is not evidence of an exploitable production service.
- **Compatibility / minimal separate PR:** `@iconify/tools@4.2.0` declares `tar: ^7.5.2`, so `7.5.21` satisfies its declared semver range. Its `untar()` helper calls the existing `tar.x({ ... })` API, and `7.5.21` remains in the same 7.x major line; this supports source/API compatibility, but does not replace a frozen-install and build verification in the separate security PR. Raise only the root `pnpm.overrides.tar` to at least `7.5.21` and refresh the lockfile there, then run frozen install, focused dependency-tree inspection, `pnpm site:test`, default/external builds, and a fresh `pnpm audit`. Do not perform that dependency change in this PR-1 implementation. Sources: [`@iconify/tools` package manifest](https://github.com/iconify/tools/blob/main/package.json), [node-tar v7.5.21 tag](https://github.com/isaacs/node-tar/releases/tag/v7.5.21).
- **Status:** The vulnerable package/version and all five applicable audit advisories are **CONFIRMED**; exploitability in KIRARI's current call graph is **NOT_REACHABLE**, with a conditional future/tooling risk. Keep the Critical dependency advisory and High recursion advisory visible as unresolved security release gates until the separate override/lockfile PR is reviewed.

## Combined security decision

Do not report a security release PASS. F3 is a conditional Critical build-time RCE path when untrusted AVIF is processed; F7 is a confirmed Critical vulnerable dependency but its archive extraction sink is not reached by the configured KIRARI build. This review does not establish that either issue has been exploited or that production was compromised.
