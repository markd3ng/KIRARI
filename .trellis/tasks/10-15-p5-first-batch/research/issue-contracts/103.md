# #103 [RM-09] Align generated CSP with documented analytics providers

## Architecture clarification — 2026-10-15

KIRARI uses the hosting provider's native deployment mechanism. GitHub Actions validates source and produces optional portable artifacts, but does not duplicate the provider's native release controller.

Independent application/tooling hardening has no P4, C1, Trusted Sources or release-binding prerequisite. Existing functional requirements and focused tests remain.

GOAL
Make the existing supported analytics configuration work under the generated Content Security Policy without weakening unrelated policy.

SCOPE
Map each existing documented provider to required script-src/connect-src origins, include documented defaults when provider source fields are omitted, and update the shared policy generator so Pages headers and Vercel configuration remain aligned. Verify optional search-ad resource needs as part of its own issue only.

OUT_OF_SCOPE
No new analytics providers, no blanket CSP relaxation/tightening, and no changes to intentional trusted-snippet inline policy absent a separate nonce migration.

ACCEPTANCE_CRITERIA
- Provider origin matrix covers currently documented integrations and exact configurable source behavior.
- Generated Pages and Vercel policies permit only the needed origins for enabled fixtures.
- Default/disabled configuration adds no provider origins beyond current baseline.
- Regression assertions verify generator and materialized outputs stay synchronized.

DEPENDENCIES
None for the concrete CSP gap; RM-12 provider choices determine runtime browser verification, but allowlist mapping can be done from documented integrations.

DELIVERY_EVIDENCE
Provider/origin matrix, generated-header/config assertions, and browser/network evidence for selected enabled providers.
