# AI-assisted Site setup

Use this checklist for a new Site or a controlled migration. Keep the Site repository separate from Core; no GUI wizard or framework is required.

1. **Choose the path.** Start a new Site from this template. If an existing Site or `packages/site-profile` tree is present, classify it as a legacy migration and keep its files read-only until approved.
2. **Initialize Core.** Run `./scripts/site-setup.sh` to check out the exact committed `.kirari/core` gitlink recursively. Never follow a branch or use `git submodule update --remote`. From the Site root, install the pinned Core dependencies with `pnpm --dir .kirari/core install --frozen-lockfile`.
3. **Bootstrap the Site.** Confirm `.kirari/site.toml` declares schema version 2, `setup-state = "ready"`, and the Core pin. Keep product settings in `kirari.config.toml`; provide `content/posts/`, `content/pages/`, `data/`, `assets/`, `public/`, and the separately trusted `snippets/` directory. Validate the committed Site input with `node .kirari/core/apps/site/scripts/check-site-contract-v2.mjs "$PWD" --core-sha "$(git -C .kirari/core rev-parse HEAD)"`.
4. **Collect owner choices.** Ask only for nonsecret Site decisions such as identity, canonical origin, default locale, and approved content. Never invent credentials, analytics identifiers, production settings, or domain ownership.
5. **Check taxonomy and locales.** The Core validator checks `data/taxonomy.json`, `data/route-aliases.json`, and `kirari.config.toml` together. Keep taxonomy IDs/slugs stable and reference IDs from content; use canonical locale IDs `en`, `zh-Hans`, `zh-Hant`, and `ja`.
6. **Inventory legacy input before writing.** Have the Core migrator produce a source-to-destination mapping and loss report first. For an existing Profile tree, run `node .kirari/core/apps/site/scripts/migrate-site-profile-v1-to-v2.mjs --source /path/to/site-profile --target /path/to/new-site --report /path/to/migration-report.json --core-sha "$(git -C .kirari/core rev-parse HEAD)"`. List every supported source, asset, route alias, and snippet. Ask the owner to approve the report; stop on blockers or ambiguous inputs and do not overwrite or delete the source.
7. **Migrate only approved content.** After reviewing a clean report, run the same migration command with `--apply` and a new report path to create the new Site tree. Exclude generated output, secrets, Core files, package metadata, and unapproved executable code; preserve the original source tree.
8. **Validate and build locally.** From the Site root, set `SITE_ROOT="$PWD"`, `SITE_SHA="$(git rev-parse HEAD)"`, and `ARTIFACT_DIR` to a new path outside the Site checkout. Then run `cd .kirari/core && ./build.sh --compose --require-site-contract-v2 --core-ref HEAD --site "$SITE_ROOT" --site-ref "$SITE_SHA" --artifact-dir "$ARTIFACT_DIR"`. Confirm the input tree was not changed. Build success does not establish rendered or browser acceptance.
9. **Report the result.** State the Core and Site revisions, validation/build status, artifact location, and unresolved owner choices. Leave unanswered values unset; never fabricate settings to make validation pass.
